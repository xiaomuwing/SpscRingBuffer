# SpscRingBuffer 开发路线

更新日期：2026-10-29（Asia/Shanghai）。

项目从原 EdgeCompute 的环形缓冲区实现中独立出来，为采集线程与处理线程提供固定容量的数据交接通道。开发围绕三件事推进：明确单生产者单消费者的使用边界，修正接口和统计中的实际问题，再通过回归测试验证正常路径与异常边界。

目前已完成独立建库、三轮审查、首轮修复和维护防御补充修复。控制台测试由 19 项扩展到 31 项，Windows X64 与 X86 验证已通过。下一阶段是业务接入、目标平台复测和实际负载下的性能评估。公共 API、调用示例和迁移要求见 [项目 readme](../readme.md)。

## 第一阶段：建立独立类库与基本契约（2026-10-08）

最初将已有实现整理为独立的 .NET 10 / 稳定 C# 14 解决方案，命名空间调整为 `EdgeCompute.Infrastructure.Buffers`。解决方案由无第三方依赖的类库和控制台测试程序组成，统计类型独立为 `RingBufferStatistics`。这一步建立了可单独构建、验证和引用的基础设施库，原业务项目的调用迁移仍需在接入时完成。

核心能力包括任意正容量、单点与批量读写、整批写入、精确读取、Peek、主动丢弃和运行统计。缓冲区满时拒绝新写入，保留队列内的数据。正常读写使用预分配数组和 Span，缓冲区自身不主动分配内存。

这一阶段确定了贯穿后续开发的线程所有权规则：所有写方法由一个生产者独占；所有读、Peek、Discard 方法由一个消费者独占；同端不得并发或重入。Clear 和 ResetStatistics 必须在停止并同步两端后执行。Count、FreeCount 和统计只用于监控，业务操作以 Try 方法的返回值为准。

实现将序号与物理索引分开维护。序号递增和差值采用 unchecked 的 64 位模运算，物理索引按尾部剩余长度环回，从而支持任意容量并避免索引加法溢出。生产者写完数组后才发布写序号；消费者复制数据、清理引用槽位后才发布读序号，保证槽位重新使用前已完成交接。

统计也在此阶段明确分工：TotalRead 记录交付给消费者的元素，TotalDiscarded 记录 Discard 和停止后 Clear 主动丢弃的元素，RejectedWrites 记录被拒绝的元素尝试数。重试会重复增加拒绝计数，交付不代表下游处理成功，这些含义不承担业务层的唯一丢样审计。

初始 19 项测试覆盖 FIFO、满空状态、容量 1、批量环回、引用释放、序号回绕、随机对照、线程分配量和双线程传输。Windows X64 上完成了启用溢出检查的 Release 构建、三轮完整测试及 30 秒混合并发长测，建立后续修改的验证基线。

## 第二阶段：通过审查确认修复范围（2026-10-28 至 2026-10-29）

初审、复核和再次复核逐步把问题聚焦到接口歧义、统计访问、内存布局和调用方进展条件。除了阅读代码，还使用独立探针、可空编译检查、状态注入及 X86 实测核对结论，避免只根据某次异常现象或性能数字确定修改方向。

确认需要处理的主要问题有：普通 long 统计写入在 32 位运行时可能出现撕裂；TryRead/TryPeek 的失败结果缺少条件可空标注；单点与批量写入同名，使某些 null、default 和数组调用产生非预期绑定；超过容量的整批请求永远无法完成；状态对象只声明布局大小，未形成预期的实际尾部空间。

审查还补充了一个调用方进展问题：整批长度都不超过容量，也不保证双方持续重试能够推进。例如容量为 4、已有 2 个元素时，写入 3 个和精确读取 3 个都会失败。如果双方始终坚持整批请求，队列会停在这一状态。因此接入协议需要部分操作回退、合适的容量条件、取消检查及生产结束后的尾部排空。

同时明确了修复边界。并发 Clear 属于违反既定所有权规则，不能靠局部序号修改变成安全操作；正常运行时统计不是一致快照，非空重置也不能直接套用从零开始的账目等式。Count 的采样可能跨越两端推进，保留范围钳制有其用途。广播、持久化、等待唤醒、覆盖旧数据和内部槽位借用属于另行设计的能力，不在本轮修复中扩大核心接口。

性能结论也随复核收窄：小容量、批量长度、对象布局和监控频率都可能影响成本，但单机未绑核的结果不足以规定通用容量下限、批量门槛或固定收益倍数。后续优化必须同时说明测试条件、语义影响和验证证据。

## 第三阶段：修正接口、统计和存储路径（2026-10-29）

首轮实现先解决可确认的正确性和易用性问题，再处理不改变线程所有权的存储优化。

累计 long 统计的写入统一改为原子访问，继续保持单写者和 unchecked 累加。Written 在发布写序号之前更新，采样先读取 Read、Discarded，再读取 Written，减少可避免的统计顺序问题；多字段近似统计的契约保持不变。

单点写入保留 `TryWrite(in T)`，部分批量写入更名为 `TryWriteBatch`，移除容易混淆的同名重载。TryRead 和 TryPeek 增加 `[MaybeNullWhen(false)]`，让失败分支的空值风险能被编译器识别。TryWriteAll 和 TryReadExact 对超过容量的请求改为立即抛出参数异常，且不修改队列、目标或拒绝计数；容量以内的暂时不足仍按原语义返回失败。

为解释维护前后的账目，统计新增 Generation 和 InitialCount。成功 Clear 或 ResetStatistics 会推进公开代次；非空重置将保留的数据记为新统计周期的期初积压。在停止并同步两端且计数未溢出的条件下，可核对：

```text
InitialCount + TotalWritten = TotalRead + TotalDiscarded + Count
```

原七参数构造与解构形式保留，新增属性参与 record 相等性。调用方需要重新构建，并检查批量写入、可空处理、统计序列化与等值判断。尤其是元素类型可接收数组对象时，旧 `TryWrite(array)` 可能仍能编译，但此时表达的是单个数组对象入队。

存储路径增加真实尾部字段，修正状态对象的填充实现；引用 Clear 从扫描整个容量改为只清实际占用区间，不跨尾部时跳过空的第二段复制或清理。保留任意容量、引用先清理后发布以及既有高水位含义，不承诺硬件缓存行对齐。

这一阶段曾引入对端序号缓存，以减少共享序号读取。它随后暴露出防御覆盖不足的问题，并在下一阶段撤回。当前版本不再采用这项优化，早期缓存版本的性能数字不代表当前实现。

首轮新增 8 项回归，测试总数达到 27 项，覆盖接口绑定、统计原子性、实际填充、引用清理、整批等待回退及并发回绕。X64、X86 重复测试与长测，以及独立探针和可空负向编译检查，均按预期完成。

## 第四阶段：补齐异常状态防御与维护采样（2026-10-29）

首轮修复后的进一步验证发现三个相互关联的缺口：Clear 会把负差值计入丢弃量；缓存快路径可能跳过实际序号检查；统计采样跨过维护时，旧计数可能被标记为新代次。这些发现推动实现从局部检查转向统一的入口验证和明确的维护边界。

### 在修改数据与账目前校验停止状态

Clear 和 ResetStatistics 共用停止状态校验：先检查完整 long 差值是否在 `0..Capacity`，再转换为 int；同时验证两端索引范围和索引与占用量的对应关系。这既拦截负差值，也防止超大差值截断后伪装成合法数量。

校验失败时抛出 InvalidOperationException，槽位、序号、索引、累计统计、InitialCount 和公开 Generation 保持不变。内部维护标记通过 finally 退出，不遗留“维护中”。合法 Clear 继续按实际占用量清理引用并计入丢弃量，合法 ResetStatistics 保留队列数据。损坏状态下不尝试猜测真实丢弃量。

### 统一检查实际观察到的对端序号

删除读写端的序号缓存。所有非空读写、Peek 和正数 Discard 每次读取对端已发布序号，在 long 范围内验证差值后才继续操作。观察到非法差值时，读端不交付数据，写端拒绝并按既有元素尝试数记账；空请求仍保持无操作语义。

这一选择增加了共享序号读取成本，但让各入口的防御行为一致，避免历史高水位或请求长度影响是否检查。它仍不能保证识别任意内存破坏、同端重入或并发维护的所有交错，调用方必须继续遵守 SPSC 契约。

### 用维护版本保护统计采样边界

新增 `TryGetStatistics(out RingBufferStatistics)`。采样未跨维护时返回 true；维护中或采样期间维护版本变化时，返回 false 和 default，由监控跳过该样本。GetStatistics 包装此接口，遇到相同冲突时抛异常，不等待或自旋重试。

维护开始前以一次 CAS 将私有版本从偶数改为奇数，完成或异常退出时恢复为下一偶数。采样先读取版本，读取统计字段后执行完整内存屏障，再检查版本；只有首尾版本相同且为偶数才交付样本。公开 Generation 仍只在成功维护时递增，用来划分监控基线。仅提前读取 Generation 无法替代这套开始和结束检测。

私有版本采用 unchecked 环回，一次采样跨完整 2^63 次维护产生的版本重复不在保证范围内。失败维护不会推进公开代次，但会让跨过该次尝试的采样失效。Clear 后再 ResetStatistics 是两次独立维护，监控可以观察到二者之间的合法状态。

最终形成的边界是：监控可与维护并发并跳过冲突样本；数据读写仍必须在维护前停止并同步，维护调用之间也应串行安排。该协议只防止维护前后字段混合，正常生产和消费期间的统计仍是近似值。

补充修复新增 4 项回归，覆盖非法差值和索引下的无副作用失败、历史状态下的逐入口检查、维护窗口及版本环回，以及 100,000 轮维护与监控交错采样。测试总数扩展到当前的 31 项。

## 第五阶段：形成当前可交付基线

截至 2026-10-29，本轮确认的问题已完成处理。当前实现保持 .NET 10 / 稳定 C# 14、零第三方依赖、任意正容量和单生产者单消费者模型。正常数据路径没有 CAS 或 lock；维护入口以一次 CAS 拒绝重叠维护。

测试体系从基础行为扩展到随机对照、引用生命周期、零线程分配、64 位序号与计数回绕、X86 统计原子性、并发载荷完整性和维护采样边界。异常注入通过停止状态下的反射完成，没有为测试增加公共入口。

后续代码修改沿用“Release 构建 → 控制台全套测试 → 并发修改补重复与长测”的顺序，在解决方案根目录执行：

独立诊断程序保留在 `docs/复核探针` 与 `docs/性能对照`，不加入产品解决方案。性能程序比较最初源码快照与当前类库，固定 long 载荷、容量 1023、每轮 500 万元素，预热后交替运行七轮并逐项校验。它没有绑定 CPU，也不覆盖频繁统计采样成本；完整版本对比不能用于归因某项优化。Baseline 源码仅供诊断，不应复制回产品。

## 下一阶段：业务接入与目标环境验证

下一阶段按接入链路推进，尚未完成的工作如下：

1. **迁移并核对业务调用。** 批量写入统一使用 TryWriteBatch；处理超容量参数和可空结果；监控使用 TryGetStatistics 并跳过失败样本，按 Generation 重建基线。检查统计序列化、等值判断及生产结束后的尾部排空。
2. **验证真实采集链路。** 核对驱动回调是否串行、两端是否可能重入、载荷内存何时归还，以及峰值速率、批次和消费者停顿。设备序号、唯一丢样审计、下游确认、持久化及故障恢复由外层链路完成。
3. **补齐目标平台和持续运行证据。** Linux/ARM64、真实硬件长期采集尚未验证。根据实际部署目标开展重复与长测，并检查停机同步、线程所有权交接和资源释放。
4. **按目标负载评估性能。** 使用真实元素类型、容量、批次、占用水平和监控频率测量吞吐、延迟与分配，控制 CPU 调度等变量。以后若重新引入缓存或布局优化，必须保留现有防御行为并补足回归证据。

核心库继续负责单通道的数据交接。广播可由外层分发到多个队列，完成与唤醒由外层同步协议提供；有序时间戳的过期前缀可由消费者结合 Peek 和 Discard 处理。覆盖旧数据、多生产者或多消费者、借用内部槽位等新能力，需要先设计所有权和生命周期协议，再单独实施验证。
